# cases/ — 康复病历库

> 目标：把每次康复治疗沉淀成一份**病历**——症状 → 处方 → 结果 → 复用要点，四段齐全、单文件自包含。下次遇到相似症状直接查病历，照抄处方与修法，不从头诊断——**越修越聪明**。
> 死规矩：**病历只收复查通过的**（知识库 [stated] 原则：不存 AI 推断）。未治疗/未复查的接诊只留 `.goal/` 工作记录，不入库。

## 误判案例（评估器判错的记录）

评估器是「必要条件闸门」，但关键词启发式判定存在**假阳性**（判过但内容不真符合）与**假阴性**（该过的没判过）。凡确认的误判，按 `references/eval-notes/_eval-misjudge-template.md` 模板记录——评估器改进与康复病历分开归档：

- **格式**：误判类型 = 假阳性/假阴性｜评估器判了什么 vs 事实｜证据（样本/命令输出）｜修正动作（已实施的具体文件改动）
- **入口**：新增文件按 `references/eval-notes/eval-misjudge-NN.md` 命名（N 从 01 递增），模板见 `references/eval-notes/_eval-misjudge-template.md`
- **死规矩**：模板里「修正动作」必须是已实施的（指向具体文件改动），不许写「待办」——没修的误判只留 `.goal/` 工作记录，不入库

## 入库规则（必须全满足）

1. **复查通过**：该 skill 康复后全量评估 + 扩展清单全过（含运行时实测），分数 ≥ 修复前
2. **有真实改动**：有实际 diff（治疗落了盘），不是「诊断完没治」
3. **格式自包含**：假设读者无任何背景（不看原 skill、不看工作区），单文件能看懂整个病历
4. **分级清楚**：标注基本型/期望型各改了哪些，为什么修（对应机制）
5. **日期 + 评估器版本**：写明日期与所用评估器（包内版本以 sha256 为准）

## 类型边界（什么算病历）

**只收「skill 康复治疗」病历**：一次完整的 症状→诊断→修法→复查 闭环，且复查通过。

- ✅ 收：skill 本体/机制层缺陷的康复（基本型/期望型修复，分数 ≥ 修复前）
- ✅ 收：跨 skill 的康复（如用 leader 执行经验体检 rehab 自身）
- ❌ 不收：**评估器自身 bug 修复**——走 guard.sh 版本管理（v3.0.1 等发版记录已覆盖），归档至 `references/eval-notes/`，不入病历库
- ❌ 不收：未治疗的诊断记录（只留 `.goal/` 工作记录）
- ❌ 不收：操作日志/流程记录（无复用价值不沉淀）

## 报备制（用户知情权）

每次康复会话结束，AI 必须向用户报备本次入库/更新的病历清单：

- 哪个 case（文件名 + 一句话摘要）
- 符合哪几条入库规则
- 是否格式合规（对照本文件模板）

用户可确认入库、要求修改、或喊停移出。**未报备不得直接入库。**

## 文件命名与格式

```
{skill名}-case-{序号}.md       例：second-brain-case-01.md
```

每个病历文件结构（自包含，含元信息）：

```
# {skill名} 康复病历 {序号}

- 日期：YYYY-MM-DD
- 评估器：包内 scripts/skill_eval.py（sha256 前缀至少 8 位）
- 症状摘要：一句话
- 分级：基本型 X 项 / 期望型 Y 项

## 一、症状（修复前）
- 修复前评分：__/100（等级）
- 未过项清单（含每项详情）

## 二、修法（按机制）
| 未过项 | 分级 | 为什么修 | 对应机制 | 具体改动 |
|:---|:---:|:---|:---|:---|

## 三、复查结果（修复后）
- 修复后评分：__/100（等级）
- 扩展清单：静态 9 项 / 五要素 / 运行时实测 各项结论
- 关键命令与输出（贴真实输出）

## 四、可复用要点
- 这个病历教会了什么（下次遇到同类症状可以直接抄哪部分）
```
