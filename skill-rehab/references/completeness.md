# completeness.md — 类别完整性清单（充分性审查）

> **定位**：评估器判「必要条件」（有没有），判不了「充分性」（全不全）。
> 本清单按 skill 类别穷尽列出「这类 skill 该有的」，AI 逐项核对，**不许「评估器没点名就跳过」**。
> 诊断与复查都必走：**评估器未过项 + 本清单缺口 = 处方**（双源合并）。

## 一、怎么用

1. **分类**：按 SKILL.md description/正文特征词判断类别（见「三、分类规则」）
2. **先过通用骨架**：所有类别先核对「二、通用六零件骨架」
3. **再过类别清单**：按类别过「四、各类别清单」
4. **每项结论四选一**：
   - `[脚本化✓]` — 已固化为脚本（SKILL.md 有声明 + 脚本文件真实存在）
   - `[命令化✓]` — 有明确可执行命令（可复制运行，退出码可判）
   - `[显式留AI✓]` — 明确写「由 AI 判断」且给理由（如语义判断无法机器化）
   - `[❌缺口]` — 该有但没有任何处理 → **进处方**
5. **两源合并**：评估器未过项 + 本清单缺口，全进治疗

## 二、通用六零件骨架（所有类别必核）

skill 工作流骨架 = 六类可写死的零件。逐项核对「有没有写死」：

| # | 零件 | 是什么 | WorkBuddy 落法 | 核对结论 |
|:--:|:---|:---|:---|:---|
| 1 | 触发 | 什么时候跑：定时 / 事件 / 手动 | 定时=automation｜事件=hook｜手动=SKILL.md 触发词 | ☐ |
| 2 | 步骤 | 什么顺序：顺序 / 分支 / 检查点 | SKILL.md 流程 + 产出物锁/闸门脚本 | ☐ |
| 3 | 材料 | 用什么料：固定输入 / 模板 | references/ 数据源 + 模板文件 | ☐ |
| 4 | 规则 | 边界+质检：权限 / 验收标准 | SKILL.md 死规矩 + 评估器 + 本清单 | ☐ |
| 5 | 工具 | 用什么手：固定连接器 / 脚本 | scripts/ + MCP 连接器 | ☐ |
| 6 | 输出 | 成品什么样：格式 / 位置 | 输出模板 + 保存路径规则 | ☐ |

**hook 事件层核对**（触发零件的强制层）：

- skill 骨架三层：SKILL.md=引导层（AI 自觉）→ scripts/=工具层（AI 调用）→ hooks/=强制层（系统自动，物理拦截）。hook 是最后防线，三层配合才完整。
- **挂 hook 判定**：某操作满足 ①违规代价高（改核心文件/发布/删数据）②AI 靠自觉容易漏（跳步/忘跑前置）→ 应挂 hook 物理拦截。
- 满足条件但无 hook → 标 `[❌事件层缺口]` 进处方；已有脚本强制的地方不必重复挂（避免冗余）。

## 五、复查闭环

- 治疗完成后：**重跑评估器**（分 ≥ 修复前，未过项清零）+ **本清单复查**（每项从 ☐ 变为 脚本化✓/命令化✓/显式留AI✓，缺口清零）
- **两源都过才算达标**——评估器满分 ≠ 完整性过；完整性过 ≠ 评估器满分。缺任一源，如实报告，不许说「做完了」。
