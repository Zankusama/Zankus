# completeness.md — 类别完整性清单（充分性审查，评估器的另一半）

> **定位**：评估器只判「必要条件」（有没有），判不了「充分性」（全不全）。
> 完整性清单按 skill 类别穷尽列出「这类 skill 该有的」，AI 逐项核对，**不许「评估器没点名就跳过」**。
> 来源：2026-08-03 用户方法论质疑——「评估器只判断有无，不把问题都找出来，修的时候不彻底」。评估器是必要条件闸门，处方必须双源。

## 怎么用（诊断/复查必走）

1. **分类**：按 SKILL.md description/正文特征词判断类别（见下方分类规则）
2. **逐项核对**：过该类清单每一项，结论三选一：
   - `[脚本化✓]` — 该操作已固化为脚本（SKILL.md 有声明 + 脚本文件真实存在）
   - `[命令化✓]` — 有明确可执行命令（可复制运行，退出码可判）
   - `[显式留AI✓]` — 明确写「由 AI 判断」且给理由（如语义判断无法机器化）
   - `[❌缺口]` — 该项该有但没有任何处理 → **进处方**
3. **两源合并**：评估器未过项 + 本清单缺口 = 处方，全进治疗

## 通用六零件骨架（所有类别必核，v1.2.1 新增）

> **来源**：2026-08-03 用户补盲——「工作流可以写死的零件」六类框架 + hook 机制调研（WorkBuddy hooks 与 Claude Code 同构，配置在 `~/.workbuddy/settings.json`，事件：UserPromptSubmit/PreToolUse/PostToolUse/Stop 等）。
> **意义**：评估器 + 分类清单只覆盖「步骤/规则/工具/输出」的部分；「触发」的**事件层（hook）**此前完全没被评估——这是 skill 骨架的强制层，评估必须纳入。
> **骨架三层**：SKILL.md=引导层（AI 自觉）→ scripts/=工具层（AI 调用）→ hooks/=强制层（系统自动，物理拦截）。hook 是「最后防线」不是「主流程」，三层配合才完整。

| # | 零件 | 是什么（写死什么）| WorkBuddy 落法 | 核对结论 |
|:--:|:---|:---|:---|:---|
| 1 | **触发** | 什么时候跑：定时 / 事件 / 手动 | 定时=自动化（automation）｜事件=**hook**（UserPromptSubmit/PreToolUse 等）｜手动=SKILL.md 触发词 | ☐ |
| 2 | **步骤** | 什么顺序：顺序 / 分支 / 检查点 | SKILL.md 流程 + 产出物锁/闸门脚本（每步产出物校验）| ☐ |
| 3 | **材料** | 用什么料：固定输入 / 模板 | references/ 指定数据源 + 模板文件 | ☐ |
| 4 | **规则** | 边界+质检：权限 / 验收标准 | SKILL.md 死规矩 + 评估器打分 + 完整性清单 | ☐ |
| 5 | **工具** | 用什么手：固定连接器 / 脚本 | scripts/ + MCP 连接器 | ☐ |
| 6 | **输出** | 成品什么样：固定格式 / 固定位置 | 输出模板 + 保存路径规则 | ☐ |

**核对方法**：六零件逐项看「有没有写死」——有 → 标实现形态（脚本化✓/命令化✓/显式留AI✓）；**「触发」零件必须回答"事件层有没有 hook"**——无 hook 但存在「AI 靠自觉但违规代价高」的操作 → 标 `[❌事件层缺口]` 进处方（hook 候选）。
**hook 候选判定**：某操作满足 ①违规代价高（改核心文件/发布/删数据）②AI 靠自觉容易漏（跳步/忘跑前置）→ 该操作应挂 hook 物理拦截，无 = 缺口。

## 复查闭环

- 治疗完成后：**重跑评估器**（分 ≥ 修复前，未过项清零）+ **本清单复查**（每项从 ☐ 变为 脚本化✓/命令化✓/显式留AI✓，缺口清零）
- **两源都过才算达标**——评估器满分 ≠ 完整性过；完整性过 ≠ 评估器满分。缺任一源，如实报告，不许说「做完了」。
