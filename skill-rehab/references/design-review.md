# design-review.md — 设计评审（源三：方向层 · 实测驱动）

> 定位：诊断三源之三——评估器查"有没有"（必要条件）、完整性清单查"该有的全不全"（充分性·结构）、**本清单查"跑起来对不对"（充分性·方向/流程）**。
> 核心原则：**问题只信跑出来的，不信读出来的。** 人自己做的 skill 没完整跑过，看不出问题在哪——AI 静态读文件同样找不到（文件写得像模像样，一跑就露馅）。所以设计评审不是"读文件答问题"，是**拿真实任务真跑一遍，从跑的过程和产出里挑毛病，再给具体建议**。
> 何时用：诊断阶段必跑（每个 skill 康复都跑一遍）；修复完复查时再跑一遍确认没修偏。
> **死规矩（产物锁，v1.7.3）**：设计评审完**必须物化** `.goal/rehab-diff/<skill>/设计评审实测记录.md`——真实任务描述 + 每一步产物/闸门结果 + 挑出的毛病。**缺这个文件 = 设计评审没完成 = 诊断不合格**（`check_rehab_report.py --dir <诊断目录>` 物理拦截，不靠自觉——防「只测脚本环节就下方向结论」的跳步）。

---

## 评审怎么跑（4 步，核心是"跑"）

### 第 1 步：拿一个真实任务当输入

- 用 skill 自己声明的典型场景，构造一个**真实任务输入**（宁可真不要假：用实际会接到的活）
- 示例：设计评审"文案审核 skill"→ 输入 = 一份真实产品文案；设计评审"写任务书 skill"→ 输入 = 一个真实的模糊需求
- ⚠️ 不许用假任务（"测试用"的任务跑不出真问题）

### 第 2 步：完整跑一遍（AI 当执行者走全流程）

- 按 skill 的 SKILL.md 流程从头走到底，**能实际执行的步骤实际执行**（跑脚本/命令/读文件），执行不了的模拟但记录"此处为模拟"
- 每步记录实际发生什么：这步做了什么、产出是什么、有没有卡住/跳过/走样
- 跑的过程 = 评审证据，不是脑补

### 第 3 步：从"跑的过程 + 最终产出"挑毛病

跑完对照两把尺子：

| 尺子 | 问什么 | 例子 |
|------|------|------|
| **过程尺** | 每一步真走了吗？有没有跳过/卡住/顺序错？ | 流程说"先检索再回答"，实际跑的时候没检索直接答了 |
| **产出尺** | 最终产出对得上"这 skill 该干的活"吗？ | 文案审核 skill 跑完，该标出的违禁词没标出 |

挑出的毛病按严重度记：**跑都跑不通**（流程缺陷）> **跑了但产出不对**（方向缺陷）> **能跑能出但可更好**（优化点）。

### 第 4 步：每条毛病 → 一条具体建议（审完给建议）

建议必须可执行，格式固定：**「在哪步发现 → 什么问题 → 怎么改」**。不许给"建议优化一下"这种空话。

| 例子：毛病 | 建议 |
|------|------|
| 跑第 2 步时，流程说要查知识库但没写查哪个/怎么查，AI 直接跳过了 | 第 2 步补具体检索指令（查哪个库/什么关键词/查不到怎么办），否则这步形同虚设 |
| 跑完产出缺"风险分级"，但 skill 承诺输出里有 | 输出模板补"风险分级"字段 + 验收命令加一条检查 |

## 评审发现的分级映射

| 评审发现 | 分级 | 例子 |
|------|:--:|------|
| 跑不通/产出方向错 | **基本型**（必改） | 流程步骤无法执行、产出对不上承诺 |
| 能跑但可更好 | **期望型**（建议） | 有更省事的做法、输出可更清晰 |
| 措辞/顺序微调 | 无差异型（跳过） | 换个说法也行 |

## 评审 vs 评估器/完整性清单的分工（边界）

| 源 | 查什么 | 怎么查 |
|:--:|------|:--:|
| 评估器 | 有没有（必要条件） | 机器读文件 |
| 完整性清单 | 该有的全不全（充分性·结构） | 机器+AI 读文件 |
| **设计评审** | **跑起来对不对（充分性·方向/流程）** | **真跑一遍**（实测驱动） |

> ⚠️ 诚实边界：设计评审只能发现"跑出来的问题"，查不了"没跑到的场景"（覆盖不到的输入/长尾情况）——那靠真实使用反馈（生命周期层）补。它保证的是：**这 skill 在它声明的场景里，真能跑通、产出真对得上承诺**——这一条静态分析永远给不了。
